# Custos — Agent Credential Vault Design

**Date:** 2026-11-17 (rev 36 — audit rounds 1–39 findings resolved)
**Status:** accepted by operator (implementation starting). Multi-model audit gate closed at round 39 without full unanimity — remaining rounds were upstream stream failures and polish; operator decision recorded in lieu of a unanimous round.
**Siblings:** Janus (LLM front door), Portunus (MCP front door). Custos is the keeper of credentials: one encrypted store that agents read and write through scoped keys, over HTTP and MCP.

**One-liner:** Self-hosted credential vault: named multi-field items, AES-GCM encryption at rest with a versioned keyring, scoped read / read-write agent keys, audit log, REST API + MCP, single operator.

**Audit history:** rounds 1–24 of the multi-model spec gate ran against this design; every round's findings were resolved in the following revision (details in the audit transcripts, kept outside the repo). This document is the current design of record.

## 1. Problem

Credentials (API keys, access-id/secret pairs, tokens) live scattered across chat histories, notes, and shell rc files. Using them with agents means pasting plaintext into conversations, which leaks them into transcripts and model providers, with no access control, no revocation, and no record of who used what. Doppler and Infisical solve team/CI problems (environments, releases, dashboards) that a single operator does not have, at a weight that is not justified here.

Agents may see plaintext values (decided): the win is central encrypted storage, per-agent scoped keys, revocation, and audit — not hiding values at use time. No injection proxy, no dynamic secrets.

## 2. Goals / non-goals

**Goals**

- Named items (`aliyun`, `tencent-cloud`, `minimax`) holding a set of fields, each flagged `secret` or `plain` (base URLs and model names travel with the key), plus free-form notes for operational gotchas.
- Agents can read **and write** (create/update/delete) via keys with mode `read` or `read-write`; scopes enforced on every operation, reads and writes alike.
- Reachable from anywhere: HTTPS behind a reverse proxy; local agents use MCP.
- Audit every access; soft-delete **and overwrite history** so agent-driven destruction is **recoverable in the common case, not guaranteed against sustained malice**: every write path keeps the 20 most recent priors per `(item_id, name)` as a rolling window — **a sustained writer (agent or stolen token) can roll it; history depth is NOT a guarantee under attack — recovery beyond the window means the last backup (≤24 h RPO, §13). Grant write scopes as destructive authority** (§5 residual). Retention never prunes within the window; hard purge and force-drop are operator-only.
- Reuse the sibling gateway project's proven crypto, key, operator-auth, and audit patterns; same stack (FastAPI + PostgreSQL).
- Operator account: username + password (Argon2id), TOTP, passkeys (WebAuthn), recovery codes, Cloudflare Turnstile — same model as the sibling products.
- Minimal operator console (login + items + keys + audit + settings) following the shared `DESIGN.md` visual system.
- Rust CLI: manage items and keys, `custos env <item>` for injection-lite into human-run scripts.

**Non-goals (v1)**

- Multi-tenancy / multiple human owners (single operator; a tenant column can be added later without breaking the API).
- Injection proxy, dynamic secrets, transit/signing engine.
- Environments, versioned releases, CI integrations (Doppler territory).
- Full console feature set of the sibling gateway; v1 console is login + items + keys + audit + settings only.
- Migration importer for existing notes: items are created by agents through the API.
- Replication / HA: one instance. **Backup unit = PostgreSQL dump + keyring + pepper** (a DB-only restore loses every `secret` value — but the dump itself exposes names, notes, plain fields, and audit: **treat dumps as sensitive**, §13); restore procedure in §13.
- Workflow engine (Temporal) or background workers: all operations are short synchronous requests; expiry/revocation checked inline; retention and rekey are operator commands (§6, §9). Revisit only if a durable-job requirement (e.g. scheduled rotation against cloud APIs) is ever added.
- Per-field scopes, quotas/billing, key sharing across operators, automated pepper rotation (§5).

**Anti-goals**

- Any anonymous or plaintext-HTTP mode outside explicit dev flags.
- Secret values or full tokens in logs, audit rows, error messages, or telemetry.
- Becoming a second gateway product: no server registry, no runner, no workflows.

## 3. Architecture

One FastAPI service (`custos`), one PostgreSQL database, one thin MCP server package. No other processes.

| Piece | Role |
|---|---|
| `custos/` (Python package) | FastAPI app: REST API, `/mcp`, vault crypto, keys/scopes, operator auth, audit |
| `alembic/` | Schema migrations, run on start (skippable via env) |
| `cli/` | `custos` operator CLI — **Rust** binary (thin client over the admin API) |
| `dashboard/` | React operator console (built to `dashboard/dist`, served by the app) |
| `packages/custos-mcp/` | TypeScript stdio MCP server wrapping the REST API, npx-able |
| `deploy/` | docker-compose (app + postgres:16-alpine), reverse-proxy snippet |

- Python ≥3.12, `uv`, FastAPI, SQLAlchemy 2 async ORM (`asyncpg`) — **all database access through the ORM/session layer, no raw SQL in route code** (Alembic migrations excepted) — Alembic, `cryptography`, `argon2-cffi`, `pyotp`, WebAuthn library, `mcp` (FastMCP mounted at `/mcp`, Streamable HTTP).
- **OpenTelemetry**: TracerProvider always installed (trace ids in logs even without an exporter); OTLP HTTP export opt-in via standard `OTEL_EXPORTER_OTLP_ENDPOINT` / `OTEL_EXPORTER_OTLP_METRICS_ENDPOINT` / `OTEL_METRICS_EXPORTER`; FastAPI + SQLAlchemy instrumentation; bad `OTEL_*` config never blocks startup. Spans carry actor/action/item-name attributes — **never field values or tokens**.
- Dashboard: React + Vite; semantic style variables per the shared `DESIGN.md` (deep-ink frame, cool-gray workspace, chartreuse accent, Geist Variable / Geist Mono, WCAG AA, reduced motion).
- TypeScript MCP package uses the official MCP SDK; config = base URL + agent key; **key supplied via env (`CUSTOS_AGENT_KEY`) or a config file that the wrapper refuses to read unless mode 0600/0400** (same discipline as the CLI session file); ships as `npx custos-mcp`.
- CLI: Rust (`clap` + `reqwest`/rustls + `serde`, `tokio`), single static binary; distributed via cargo/release binaries.

**Bind/TLS contract (normative):** default bind `127.0.0.1:8300`. A **non-loopback bind requires `CUSTOS_PUBLIC_BIND=1`** — the operator asserts TLS terminates upstream (reverse proxy); the compose example uses this on a private docker network. **`CUSTOS_INSECURE_DEV=1` is plaintext dev mode and is accepted only with a loopback bind** (non-loopback + dev flag → startup failure, even with `CUSTOS_PUBLIC_BIND`); it never authorizes a non-loopback bind. Without `CUSTOS_PUBLIC_BIND=1`, a non-loopback bind is a **startup failure** with a clear message. **`CUSTOS_PUBLIC_BIND=1` is an operator assertion, not a verification — no runtime TLS probing; a mis-set flag ships plaintext (operator error, same class as a misconfigured proxy).** The two flags are **mutually exclusive** (both set → startup failure). `CUSTOS_INSECURE_DEV=1` also implies `CUSTOS_INSECURE_COOKIE=1` (browsers reject Secure cookies over HTTP). **Dev mode + Turnstile configured → startup failure** (the HTTPS widget cannot load on an HTTP page — mixed content; dev runs without Turnstile). There is no runtime "TLS detection"; the flags are the contract. `CUSTOS_BIND` is an address only (no port); port comes from `CUSTOS_PORT` (default 8300); a `host:port` value in `CUSTOS_BIND` is a config error. **Loopback classifier (pinned): the bind address must be an IP literal in `127.0.0.0/8` or `::1`, or the exact name `localhost` — which is resolved once at startup via the system resolver and every returned address must be loopback (any non-loopback result → config error); no per-request resolution.**

**Deployment contract:** exactly **one uvicorn worker process** (the rate limiter is in-process; sessions, step-up, and run tokens are DB-backed). Scaling out requires moving the limiter to shared storage first — out of scope for v1.

**Browser hardening:** uvicorn/FastAPI **access logs never include request/response bodies** (default; pinned — covers `/mcp` and all routes); **query strings are redacted from access logs too** (paths logged without `?…` — search terms can be secret-shaped; no credential ever travels in a URL outside the device-code fragment, which never reaches the server); session cookie `HttpOnly; Secure; SameSite=Lax`; **every `/api/*` and `/mcp` response carries `Cache-Control: no-store` and `Vary: Cookie, Authorization` via middleware** (blanket rule — covers value reads, agent write echoes, key/token mint, transfer-code approve, recovery-code rotation, `auth/status`, and all MCP responses; no plaintext secret or CSRF token in any browser/intermediary cache; static console assets are the only exemption — **contract: hashed Vite assets `Cache-Control: public, max-age=31536000, immutable`; the SPA shell `index.html` `no-store`; no service worker in v1; the exemption matches static file paths only, never `/api/*` or `/mcp`**); `CUSTOS_INSECURE_COOKIE=1` is **rejected at startup unless `CUSTOS_INSECURE_DEV=1` and a loopback bind** (dev mode implies it). CSP: `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; font-src 'self'; img-src 'self' data:; connect-src 'self'; frame-ancestors 'none'` (inline style attributes allowed for React; no inline scripts); **when Turnstile is configured**, additionally `https://challenges.cloudflare.com` in `script-src`, `frame-src`, `connect-src` (tested with and without). All item/field/notes strings rendered as plain text (no `dangerouslySetInnerHTML`, no markdown-to-HTML of agent-authored content). **No CORS: the app emits no `Access-Control-Allow-*` header and installs no CORS middleware (same-origin console only); cookie-authenticated mutations additionally reject a cross-site `Origin`/`Referer` when present → 403.** **CSRF**: the login/setup response body returns `csrf_token` (kept in SPA memory; CLI stores it in the session file); **auth shapes (closed list): agent plane = bearer only; admin plane = cookie+CSRF on mutations, or `co-` bearer; `x-step-up-token` may ride either admin shape (bound-principal check applies); unauthenticated auth endpoints take no CSRF (device-exchange mints the cookie+csrf pair itself); a request presenting both cookie and bearer → 401**; **`GET /api/auth/status` additionally returns `csrf_token` when called with a live session cookie** (page-refresh recovery; E2E covers reload-then-mutate); header `x-csrf-token` required on cookie-authenticated mutations only — **every authenticated `POST`/`PUT`/`PATCH`/`DELETE` under `/api/auth/*` and `/api/admin/*`; same-origin XSS reading the token via `auth/status` is out of scope (CSP is the XSS control; CSRF defends cross-site only, §11)**; bearer requests carry no CSRF; a request presenting both cookie and bearer → 401.

## 4. Crypto and storage

AES-256-GCM everywhere; blob = `nonce(12) || ciphertext+tag`. **Nonce: fresh 96-bit CSPRNG random per seal — never derived from ids/counters, never reused across re-seals** (unit-tested for uniqueness across concurrent seals). Keyring env `CUSTOS_SECRETS_KEY` = comma-separated `k<n>:<key>` where `<key>` is **base64url per RFC 4648 §5 without padding (`-`/`_` alphabet; `+`/`/`/`=` rejected), decoding to exactly 32 bytes**; `n` is a **positive decimal integer, compared numerically (k10 > k2), max wins** for sealing; duplicate `n`, malformed entries, or wrong key length → **startup failure**; older versions stay readable. **File form (`CUSTOS_SECRETS_KEY_FILE`): byte-identical content — the same comma-separated string; surrounding whitespace and `#`-comment lines ignored. Env and file both set → startup failure** (no silent precedence).

Three AAD domains, one keyring:
- **Field blobs:** AAD = `f"field:{field_id}|{key_version}"`. Moving a ciphertext to another row fails decryption.
- **History blobs:** AAD = `f"fieldh:{history_id}|{key_version}"`. History append **decrypts the prior value and re-seals under the history AAD in the same transaction, under the newest keyring version** (the append already holds the write lock and keyring; `key_version` on the history row records that newest version — rekey later moves it like any other row). (writes already require the keyring; if the source version is unavailable the write fails, see below). A history blob can never be swapped into a live field.
- **Operator-sealed blobs** (TOTP secret): key derived per version via `HKDF-SHA256(ikm=keyring[n], salt=<empty>, info="custos-operator-seal|v1")`; AAD = `f"operator:totp|{key_version}"`; `totp_key_version` column stores the version. `rekey` re-seals these too. No Fernet; one cipher family. **All three AAD formats are frozen exactly as written above (each carries its `|{key_version}` suffix); `hmac.compare_digest` is the sole primitive for comparing a presented secret/digest against a stored value** (code-review criterion). **Exempt: indexed equality lookups on stored preimage hashes (`operator_sessions.token_hash`, `device_codes.code_hash`, `step_up_tokens.nonce_hash`) — SHA-256 of a ≥128-bit random token needs no constant-time compare; the lookup key is the hash, never the plaintext.** **`device_codes.transfer_hash` is matched in application code with `compare_digest` after fetching the row by device code; the consume UPDATE then guards on `consumed_at`/attempts/window only.**

Pepper: `CUSTOS_PEPPER_FILE` or `CUSTOS_PEPPER` — **both forms are base64url without padding, decoding to ≥32 bytes of CSPRNG output** (file whitespace stripped; **both set → startup failure**, same rule as the keyring; **startup rejects an all-zero pepper and warns on any repeated-byte pattern — heuristic, not an entropy proof; generate with **`openssl rand 32 | basenc --base64url -w0 | tr -d '='`** (or `openssl rand -base64 32 | tr '+/' '-_' | tr -d '='`) — plain `-base64` output is rejected, documented**). Digest contract: `HMAC-SHA256(key=decoded pepper bytes, msg=UTF-8 of the credential's secret string exactly as presented)` — **for agent keys and operator tokens that is the base64url text after the `.` separator, byte-for-byte as received, not the decoded 32 bytes**; recovery codes use the normalized text (§5). **v1 supports no automated pepper rotation**: rotating the pepper invalidates every agent key, operator token, and recovery code. Runbook: maintenance window → rotate pepper → re-mint all keys/tokens → re-issue recovery codes (§13).

Only `secret` fields are encrypted. `plain` fields, item names, and notes are cleartext columns (metadata; list/search work without decryption).

### Schema (initial Alembic migration)

| Table | Columns (essentials) |
|---|---|
| `items` | `id` uuid pk, `name` text unique (`^[a-z0-9][a-z0-9._-]{0,199}$`), `notes` text, `revision` int (bumped on every write), `created_at`, `updated_at`, `deleted_at` (soft-delete) |
| `fields` | `id` uuid pk, `item_id` fk cascade, `name` text (**`^[A-Z][A-Z0-9_]{0,63}$`**), `secret` bool, `value` text (plain), `ciphertext` bytea + `key_version` int (secret), unique (`item_id`, `name`); **CHECK: exactly one of `value` / `ciphertext` non-null, matching `secret`** — retype executes as delete-flush-insert in one transaction (the DELETE is flushed before the INSERT — unique `(item_id, name)` never collides), so no intermediate state violates the CHECK |
| `field_history` | `id`, `field_id` (**plain uuid, no FK cascade** — snapshot identity), `item_id` (**no cascade**; rows survive field/item deletion until purge/retention — **purge deletes history rows first, then fields, then the item row, in one transaction; no FK is ever violated**), `name`, `secret`, `value`/`ciphertext`+`key_version` (same CHECK, history AAD), `superseded_at`, `superseded_by` (**text NOT NULL, same encoding as `audit.actor_id`; written only on history rows — a no-op write produces none**), `actor_label` (snapshot of key label / "operator" at write time — survives key revocation/pepper rotation) |
| `agent_keys` | `id` uuid pk, `key_id` text unique, `digest` bytea (HMAC-SHA256(pepper, secret)), `label`, `mode` enum `read`/`read-write`, `scopes` text[] (fnmatch patterns), `expires_at` nullable, `revoked_at` nullable, `created_at` |
| `operator_tokens` | same shape as `agent_keys` minus mode/scopes, plus `allow_sensitive` bool; prefix `co-`; **separate table — an agent key can never authenticate on the admin plane and vice versa** (prefix + table lookup) |
| `operator_account` | single row: `id` int pk (**constant 1, CHECK-enforced — also the keyset key for rekey cursors, table `operator_account`**), `username`, `password_hash` (**Argon2id: memory 64 MiB, iterations 3, parallelism 4** — sibling-project parameters), `totp_secret` (sealed, §4), `totp_key_version` int, `totp_enabled`, `totp_last_step_login`, `totp_last_step_stepup`, `totp_last_step_confirm` (**per-site replay counters, all `NOT NULL DEFAULT 0`**; password-change consumes a step-up token — no separate site), timestamps |
| `operator_sessions` | `id`, `token_hash` (SHA-256 of opaque cookie), `csrf_token` (**32 random bytes base64url, CSPRNG; stored on the session row; constant-time compare; minted fresh per session — login/promotion/device-exchange each produce a new one; never rotated mid-session**), `purpose` enum `full`/`recovery_reset`, `idle_ttl_seconds` int (default 43200; device-exchange sessions 3600 — idle expiry = `last_seen_at + idle_ttl_seconds`; **`recovery_reset` sessions store 0 = idle check disabled, fixed absolute window only**), `created_at`, `last_seen_at` (refreshed on every authenticated request; **`recovery_reset` sessions never refresh — fixed window: `absolute_expires_at = created_at + 30 min`, idle check disabled**), `absolute_expires_at`, `revoked_at` nullable — **invalidation sets `revoked_at`; rows are never deleted on logout/password change/reset**; expired/revoked rows pruned only by operator retention — **`actor_id` resolution is best-effort after pruning; `actor_label` snapshots are the durable attribution** |
| `step_up_tokens` | `id`, `session_id` fk nullable, `operator_token_id` fk nullable (exactly one non-null), `nonce_hash`, `kind` enum `single`/`rekey_run` (**one run kind accepted by both `/rekey` and `/rekey/verify`; cursors are endpoint-tagged and not interchangeable**), `expires_at`, `consumed_at` (null for `rekey_run` until expiry) — §5 |
| `device_codes` | `id`, `code_hash` (≥128-bit device code), `transfer_hash` nullable (set at approval), `approved_by_session` nullable, `approved_at` nullable (transfer-code TTL base), `exchange_attempts` int (**every exchange attempt — match or mismatch — first commits a guarded increment; the 5th attempt is the last: consume requires the post-increment value ≤ 5 (try 5 increments 4→5, passes; try 6 increments 5→6, fails — exactly five tries)**), `client_ip`, `user_agent` (captured at mint; **shown on the approve page as the exact IP + browser-family/OS summary parsed from the UA — the raw UA string is never rendered**), `created_at`, `expires_at` (5 min), `consumed_at` — CLI login hand-off (§5) |
| `lockout_suppressions` | `id`, `scope` (`ip:<addr>` / `ip:*` wildcard / `account`), `suppressed_until_events_ts` — break-glass unlock marker: lockout queries ignore `auth_events` at or before this ts (`ip:*` matches every IP); **the unlock path never deletes ledger rows** (operator retention is the only deleter, §6; pruning old events can only shrink active windows, never extend them) |
| `passkey_credentials` | WebAuthn credential id, public key, sign count, label, timestamps |
| `webauthn_challenges` | `id`, `challenge` bytea, `purpose` enum `register`/`assert`, `session_id` nullable (null = anonymous assertion), `expires_at` (2 min), `consumed_at` — single-use guarded consume (§6); expired rows pruned by retention |
| `recovery_codes` | `id`, `digest` (HMAC-SHA256(pepper, normalized code)), `consumed_at` — atomic single-use (§5) |
| `auth_events` | kind (`login_password`/`login_totp`/`login_passkey`/`login_recovery`/`step_up`/`agent_auth`/`setup`), `ok`, `ip` (resolved client), `peer_ip` (direct), `ts` — drives lockout |
| `audit` | `id` bigserial, `ts`, `actor_kind` (`agent`/`operator_session`/`operator_token`/`anonymous`/`local_process`), `actor_id` **text nullable — encoding pinned per kind: agent/operator_token = the 12-hex `key_id`; operator_session = session uuid as lowercase hyphenated text; local_process = `"local"`; anonymous = NULL**, `actor_label` (snapshot at write time), `action` (enumerated below), `item_name` nullable, `ok` bool, `detail` jsonb (never values) |

**Audit actions (closed enum):** `list`, `search`, `get`, `env`, `create`, `put` (replace/upsert), `patch`, `delete`, `restore`, `purge`, `force_drop`, `history`, `reveal` (item or history snapshot), `device.login` (device-code mint/approve/exchange), `key.mint`, `key.revoke`, `key.list`, `token.mint`, `token.revoke`, `token.list`, `operator.login`, `operator.logout`, `operator.step_up`, `operator.password_change`, `operator.totp_change`, `operator.passkey_change`, `operator.recovery_regen`, `operator.setup`, `account.unlock`, `rekey`, **`rekey_verify`** (each verify run audited once at start, with principal + allow_sensitive flag), `retention`, `auth.failure`. **Admin credential inventories (`GET /keys`, `/tokens`) are audited (`key.list`/`token.list` — reconnaissance by a stolen token leaves a trace); other enumeration reads (masked item get/list, `/audit`, `/rekey/audit`) are not audited individually — audit covers credential reads (get/env/reveal), all writes, all auth events, credential inventories, and destructive/maintenance runs; §2's "audit every access" means exactly this set. Agent `list`/`search` are audited (`list`/`search`, result counts only).** Failed agent authentication is audited as `auth.failure` (actor `anonymous`, ip in detail). `auth_events` is the lockout ledger; `audit` is the operator-visible record — credential failures appear in both; **ledger/audit rows for failures commit in an independent transaction before the error response** (never rolled back with the failing request; **if the ledger write itself fails, the credential request still fails closed — 503, never a success — and the failure is logged without values**). **Turnstile verdict failures produce an `audit` row only** (no `auth_events` row, hence never counted by lockout). `local_process` actions use fixed `actor_id = "local"`, `actor_label = "break-glass"`.

**Limits (normative, reconciled):**
- Field value ≤ **16 KiB** and `notes` ≤ **4 KiB**, both measured as **raw UTF-8 byte length** (all string inputs must be valid UTF-8/JSON — invalid → 422 `invalid` at the API boundary); item ≤ **32 fields**; item total ≤ **256 KiB measured on the canonical JSON of the resulting item** (`ensure_ascii` escaping counted), enforced on every write — for PATCH, measured on the **post-merge item**, not the ops body (request-body cap 2 MiB applies to all). **The measured object is always the fully-materialized resulting item (all three keys present; `notes` = the stored/updated string, never absent; **`""` is a value, counted as `""` — never normalized to absent**; kept secret values substituted from the store) — a no-op write on a fully readable item measures identically and passes; **in degraded mode even a no-op write fails (values cannot be materialized)**. Metadata-only writes (restore, soft-delete) skip the item cap entirely** (no values change; degraded restore must work). PATCH cannot grow an item past what PUT could send.
- Request body ≤ 2 MiB; single-item response/MCP tool result ≤ 1 MiB — a legal item (≤256 KiB escaped) always fits **as JSON**. **`/env` output is exempt from the 1 MiB assertion** (POSIX escaping expands each `'` ×4, so a legal item can render up to ~1 MiB of quotes): the env endpoints (agent + admin) and `custos_env` bound output at **4 MiB**, enforced per-route at serialization (over-cap → 413 `payload_too_large`) — mathematically unreachable for legal items (256 KiB × 4), a defensive assertion only.
- List/search pages carry **metadata only** (no values; **`notes` truncated to 256 chars in every list row, agent and admin planes alike**): ≤100 entries × bounded metadata (name ≤200 B, notes ≤256 chars, ≤32 field names × ≤64 B, timestamps) ≈ ≤110 KB/page worst case — two orders below 1 MiB. **The 1 MiB cap is enforced defensively regardless (oversize → 413, never a silently truncated page).** `GET /api/items/{name}` returns full notes; **the masked admin get also returns full notes** (notes are cleartext metadata by design, §4).
- Exceeding **any** of the four item caps or the request-body cap → **413 `payload_too_large`**. The **canonical item object** for size measurement is exactly `{"name":…,"notes":…,"fields":[{"name":…,"secret":…,"value":…}]}` (object keys sorted, **`fields` array sorted by name**, `ensure_ascii`, no whitespace; secret values counted as their plaintext). The 1 MiB response cap is defensive, unreachable for legal payloads.

**Soft-delete semantics (normative):**
- `DELETE` sets `items.deleted_at`. The name stays reserved (unique index includes deleted rows).
- All agent-plane **named-item** verbs (GET/PUT/PATCH/DELETE/env) on a soft-deleted item → 404 `not_found` **after scope and mode checks pass** (read-only key on in-scope soft-deleted write → 403; mode precedes existence); **`GET /api/items` and `GET /api/search` exclude soft-deleted items entirely** (collection verbs have no 404 path); except create-shaped calls (`POST`, upsert-create path) on an **in-scope** soft-deleted name → 409 `conflict`; out-of-scope → 404 (**check order, normative: scope → mode → existence/uniqueness** — a read-only key writing out-of-scope gets 404, never 403).
- Recreating a deleted name requires operator `restore` (then edit) or `purge` (then create). This name-squatting window is accepted (reversible deletion, not a rename tool).

**Overwrite history:** every PUT/PATCH that **actually changes a field's stored value or removes the field** appends the prior value to `field_history` (re-sealed under the history AAD; **the history row keeps the old `secret` flag — it is the decrypt oracle for that blob**; a retype via the sanctioned pair always snapshots the removed row (old flag, old value — even when the re-added value is identical). **Resending an identical value with an identical flag is a no-op for history** (benign repeated writes cannot evict real priors). **The item row is locked (`SELECT … FOR UPDATE`) for the whole write transaction** — history append, budget eviction, and revision bump are serialized per item. `superseded_by` = actor id (`key_id` for agent/operator-token principals — 12-hex, same encoding as `audit.actor_id`; session uuid text; `"local"`); `actor_label` snapshots the label so attribution survives revocation/pepper rotation. **History budget: 20 snapshots per `(item_id, field name)` — keyed by name across field-row ids, so remove+re-add cannot reset the budget** (supporting index on `(item_id, name)`); appending beyond evicts the oldest. **Global history ceiling: 100 000 `field_history` rows — a write that would append beyond it fails 429 `history_budget_exceeded` (operator remedy: retention/purge); bounds agent-triggered storage amplification via mint-create-delete loops.** — an accepted, bounded exception to non-destruction (§2), audited in the write's `detail` (`evicted: n` **plus the evicted snapshot ids**). **Agent-plane write responses contain only caller-supplied values; kept secret fields are `{name, secret: true, kept: true}` placeholders (no decryption for the echo) — never any prior/history value (§11 invariant, tested).** Operator-only `GET /api/admin/items/{name}/history` lists snapshots (metadata); `GET /api/admin/items/{name}/history/{id}/reveal` (**step-up**, one token per snapshot) returns one snapshot's values. `custos history <name>` likewise. Purge and retention are operator-only destructive paths.

**All HMAC-signed cursors (pagination + rekey/verify) use the pepper as key — pepper rotation invalidates every outstanding cursor (accepted: maintenance-window operation; list cursors are re-fetched, rekey resumes from a fresh cursor at the last reported position or restarts — idempotent).** **Every item write is one transaction — all ops apply or none do** (not just the downgrade refusal). **Concurrency:** `items.revision` increments on every write. **Wire format: item responses carry `ETag: "<revision>"` (quoted entity-tag); PUT/PATCH accept optional `If-Match: "<revision>"` (strict entity-tag parsing; malformed → 422 `invalid`)**; **the comparison happens under the item row lock (`SELECT … FOR UPDATE`) inside the write transaction — concurrent same-revision writers: first wins, second gets 409**; mismatch → 409 `conflict` with current revision. Without `If-Match`: last-write-wins, and the audit `detail` records the pre-write revision. **Audit `detail` keys are a closed set per action: revisions (`pre_revision`), counts (`evicted`, `dropped_unreadable`, `codes_consumed`, result counts), ids (evicted snapshot ids, key_id), flags (`break_glass`, `allow_sensitive`), ip, **device-flow stage (`mint`/`lookup`/`approve`/`exchange`) and failure reason codes (`expired`/`consumed`/`mismatch`/`attempts`/`turnstile` — enum strings, never payloads)** — never values, notes text, or search terms.** The console always sends `If-Match`.

**Missing key version / unreadable rows:** at startup the service computes referenced `key_version`s (**`SELECT DISTINCT key_version` over `fields`, `field_history`, `operator_account` — indexed metadata scan, no decryption; counts logged; O(distinct versions), cheap on any vault size**); if any are absent from the keyring it **refuses to serve** unless `CUSTOS_ALLOW_MISSING_KEY_VERSION=1` (explicit degraded mode). **"Unreadable" is defined as: referenced version absent from the keyring, OR decryption/AAD/tag failure with an available version** (corruption) — both map to 500 `key_unavailable` wherever a value must be produced. Corruption needs no startup flag: it is detected at read/write time and reported by `GET /api/admin/rekey/audit` (per-version row counts, SQL-only) **only when the version is missing**; corruption under an available version surfaces at read/write time, in rekey `skipped`, **and via `POST /rekey/verify` — the remote operator's discovery path, no shell needed**. In degraded mode: **value-producing reads** of affected items (agent get/env, reveal, history reveal) → 500 `key_unavailable` (audited; **scope is checked first, so out-of-scope callers still get the uniform 404** — the invariant holds); **masked admin get and history metadata always succeed** — unreadable secret fields render as `{name, secret: true, unavailable: true}` on the **masked get only**; **list/search rows never carry `unavailable` and never decrypt or trial-decrypt anything (pure metadata columns; collection reads work vault-wide in degraded mode)**; writes to an item holding any unreadable field fail with 500 `key_unavailable` — **including notes-only edits, new fields, and kept-value writes** (the canonical-JSON cap must measure every value — that alone blocks the write; history append would additionally need decryption when a value changes); soft-delete succeeds (metadata-only). **Operator metadata-only writes are exempt from the 500 rule: restore, soft-delete, purge, and force-drop work on items with unreadable fields, in live or soft-deleted state** (force-drop keeps the item row and its `deleted_at` state as-is). **Error precedence (normative): authentication → authorization (scope/mode/session/step-up) → state/conflict → value materialization. A request failing an auth/gate check returns that gate's status (401/403/409) even if the item also holds unreadable values; `key_unavailable` fires only after all gates pass.** **Escape: operator-only `POST /api/admin/items/{name}/force-drop` (session + step-up only — no token path, §5/§6)** — **deletes every unreadable field row and every unreadable history row of the item, including history rows whose live field is readable — detection is trial decryption of that one item's rows only (bounded: ≤32 fields + their history), never a vault scan; readable rows are never dropped** (never nulls columns — the CHECK holds), keeping readable fields/history and the live item row with its name reservation; audited **`force_drop`** (distinct from full `purge`), detail `dropped_unreadable: n`; this is the remedy for corruption or a lost key version, short of full purge. **Take a `pg_dump` before force-drop — deleted rows are unrecoverable, and under sustained writes the pre-corruption prior may already have rolled out of the 20-budget (§13).** `custos rekey --audit` calls `GET /api/admin/rekey/audit`; rekey counts undecryptable rows in `skipped` and terminates. Startup never silently proceeds.

**Rekey:** `POST /api/admin/rekey` re-seals up to **200 rows per call** (fields + history + operator-sealed blobs) under the newest key version, **updating `key_version` transactionally with the blob**; response `{remaining: n, skipped: m, run_token?, cursor?}` — **`remaining` counts rows with `key_version != newest` strictly ahead of the run cursor** (an upper bound including undecryptable ones — no decrypt scan); **termination is cursor exhaustion** (`remaining: 0` when the cursor passes the last row), so undecryptable rows never stall the loop; **`skipped` is per-call** (undecryptable rows encountered in this batch). **Batch selection is indexed, not decrypt-scanning:** pick up to 200 rows with `key_version != newest` ordered by `(table, id)` (**higher-than-keyring versions are selected too and counted as skipped** — restored-from-newer-dump case); **the run carries a keyset cursor (last processed `(table, id)`, passed back by the client as `cursor` on the next call alongside the run token) so skipped rows are never reselected — termination is guaranteed even with >200 undecryptable rows**; trial decryption happens only on the selected rows. **Each re-seal is a guarded UPDATE (`WHERE id = :id AND key_version = :old AND <value/ciphertext unchanged>` — row lock held): a concurrent write between selection and update makes it a no-op (counted neither remaining-blocking nor skipped; the row is already newest or handled by the write path).** Rows whose current version is unavailable (degraded mode) are **skipped and counted**, never blocking termination; their remedy is `force-drop` or restoring the missing key (§13). **`GET /rekey/audit` counts are SQL-only** (GROUP BY `key_version` per table — metadata columns, no decryption, cheap on any vault size); corruption with an available version is discovered at read/write time, by rekey `skipped`, **and by `POST /rekey/verify`** — not by the SQL-only audit endpoint. **Authorization:** an `allow_sensitive` operator token suffices for every batch; a session consumes one step-up on the first batch — **the `single` token's guarded consume (`consumed_at IS NULL → now()`) and the `rekey_run` insert commit in one transaction**; later batches validate the run row without consuming it (`step_up_tokens.kind`, TTL 30 min, bound to the principal, multi-use for rekey only; **each successful batch extends the run row's expiry by 30 min — the run deadline is the run row, not the session's idle clock; session liveness is still re-checked per batch. If the run token expires mid-vault, consume a fresh step-up to mint a new run and resume from the last returned cursor (cursors are principal-bound, not run-bound)**). **The first batch's response includes `run_token` (the opaque token, returned once; ≥128-bit entropy, SHA-256 `nonce_hash` stored like step-up tokens) and `cursor`; subsequent batches present the token as `x-step-up-token` and the cursor in the body** (same header, same presenter-binding check; `kind: rekey_run` accepts rekey and verify; **cursors bind to principal + endpoint only, never to a run row**). **`allow_sensitive`-token runs use the same cursor mechanics returned in each response (no run row needed). Cursor format (pinned): base64url of `{endpoint, table, last_id, plane}` + HMAC-SHA256(pepper) tag; the server verifies the tag, that `plane` matches the presenting auth plane (`session` or the operator-token `key_id`), and that `endpoint` matches the route — mismatch → 401. **Cursors bind to the plane, not the session row (session rotation keeps them valid). Cross-principal cursor replay is harmless: the payload carries only a scan position over non-secret rows — no values, no authority; every batch still requires a live run token/`allow_sensitive` principal.** **Presenter binding (definition, applies to step-up and run tokens alike): the token row records the session id or operator-token id at issuance; every consumption re-checks the presenting principal's id equals it and that the principal is still live (session unexpired/unrevoked, token unrevoked/unexpired).** Step-up tokens are likewise **32 random bytes base64url (≥128-bit)**, hashed at rest. `custos rekey` loops until `remaining: 0` **and exits nonzero if any batch reported `skipped > 0`**; after the loop the CLI **runs one final `GET /rekey/audit` and reports any rows still under non-newest versions** (a write racing a batch can leave a row behind the advanced cursor — rerun rekey if the audit is nonzero; §13's removal gate is the audit, not the loop exit). Idempotent, resumable; interruption leaves mixed versions — all readable; rerun. **One active run per vault: a second first-batch attempt while an unexpired `rekey_run` row exists → 409 `conflict` (concurrent runs cannot interleave cursors; wait for expiry or finish the run).** **`custos rekey --verify` maps to `POST /api/admin/rekey/verify`** (authorization identical to rekey: `allow_sensitive` token, or session step-up minting a `rekey_run` token; same cursor mechanics, 200 rows/batch; trial-decrypts **all** rows including newest-version ones, re-seals nothing; **selection order for both endpoints is the fixed table order `fields` → `field_history` → `operator_account`, then `id` ascending within each table; verify's `remaining` = all rows ahead of the cursor (every row is visited)**; response `{remaining, unreadable: {fields, history, operator}, run_token?, cursor?}` — **first batch returns `run_token` exactly like rekey**; listed in §6) — the only proof against corruption under the newest version.

## 5. Auth

### Agent keys

`cu-<key_id>.<secret>` — `key_id` = 12 hex chars, `secret` = **32 random bytes, base64url** (≥256-bit entropy). Bearer on every request, **including every `/mcp` request/tool call** (Streamable HTTP sessions do not cache authentication; revocation bites on the next request). Verify: look up `key_id`, HMAC per §4 digest contract, single `hmac.compare_digest`; **unknown key_id / revoked / expired paths still run `compare_digest` against a fixed dummy digest** so all failure paths do equal digest work; **the DB-lookup timing difference for unknown ids is accepted residual** (key_ids are not secret; the secret is the credential). All failures → **one identical 401**. Failed auth feeds the per-IP limiter and `auth_events` — **exactly one `agent_auth` row per request that reaches credential verification and fails** (429-gated requests produce none, §5 lockout).

- `mode`: `read` → GET/list/search/env only; **a write verb in scope → 403 `read_only`** (out-of-scope still 404 first). `read-write` → also POST/PUT/PATCH/DELETE. Never restore/purge/history, never key management.
- `scopes`: **Python `fnmatch.fnmatchcase` semantics, pinned** (`*`, `?`, `[seq]`; case-sensitive; `*` matches any characters including `.` — item names have no `/`) against the full item name (`aliyun`, `stock-*`, `*`). Empty scopes = no access (fail closed). **Enforced on reads and writes**: every named operation (including create) checks scope first; out-of-scope → 404 `not_found` — identical to missing; no existence oracle. List/search filtered to scope. Out-of-scope 404s are audited (`ok: false`) so probing is visible.

### Operator account

Database account (sibling-project pattern, copied):

- **Setup:** `POST /api/auth/setup` takes `{username, password, setup_code}` (username same grammar as item names; **password ≥ 12 characters, no composition rules** — enforced identically at setup, password change, and break-glass reset; `CUSTOS_OPERATOR_PASSWORD` (or its `_FILE` form), when set, must satisfy it too or startup fails). Body `password` is **optional iff `CUSTOS_OPERATOR_PASSWORD` is set** (then it supplies the initial password); **both present → 422 `invalid`; both absent → 422 `invalid`**. Requires a one-shot **setup code** (**≥128-bit entropy** when generated; **an operator-supplied `CUSTOS_SETUP_CODE` must be ≥22 base64url chars (128 bits) — startup rejects shorter**; `compare_digest` verification): **`CUSTOS_SETUP_CODE` env takes precedence**; absent it, a code is generated at first startup and written **only to a 0600 file** `setup-code` under `CUSTOS_DATA_DIR` — never to stderr/stdout or application logs. **Restart before setup completes reuses the existing file** (a new code is generated only when no file exists); The file is created 0600 (creation mode enforced, not just convention) and deleted on successful setup. Race-safe: single insert guarded by the single-row constraint; once an account exists the endpoint returns 403 `setup_complete` forever (audited). **The generated setup code is consumed on success (file deleted); a static `CUSTOS_SETUP_CODE` is likewise single-use (the account row is the guard).** Setup is exempt from Turnstile (the setup code is the gate) but feeds lockout (`setup` kind; **per-IP only — no account exists yet**, so the per-account window cannot apply) **and has its own tighter bucket: 3 req/min/IP plus a global 10 setup attempts/min across all IPs** (excess → 429, no ledger row). Optional bootstrap `CUSTOS_OPERATOR_PASSWORD` is accepted as the initial password (in place of the body field) only when accompanied by the setup code, and never after setup completes.
- **Login:** `POST /api/auth/login` takes `{username, password, totp?, recovery_code?}` — **at most one of `totp`/`recovery_code`; both present → 422 `invalid`**; `recovery_code?` takes the recovery path (consumed only on full success, §5 recovery codes), `totp` the TOTP path; **TOTP enabled and neither factor supplied → the identical 401 with one `login_totp` row — password alone never mints a session when TOTP is enabled**; unknown user, bad password, bad TOTP/recovery code → one identical 401. **When Turnstile is configured the body also carries `turnstile` (the widget response token); verification runs before credential checks — missing/failed token → 422 `turnstile_failed`, never the 401 shape, and no credential-failure event.** Passkey assertion carries the same `turnstile` field with the same order. **One failed request = one `auth_events` row**, kind = the stage that failed (`login_password` first; then `login_totp` or `login_recovery` per the submitted factor) — never two. **`GET /api/auth/status` includes `totp_required`** (single-operator product; the console renders the TOTP field from it). A TOTP code supplied while TOTP is disabled is **ignored** (not a failure). Alternatives: passkey (WebAuthn discoverable), or **username + password + an unused recovery code** (the code replaces the TOTP factor, never the password — a bare code cannot mint a session). **Turnstile** token required on **browser credential endpoints** (password login, passkey assertion, recovery login) when configured; **step-up and device-exchange are exempt** (already-authenticated session / transfer-code gated); **device-code mint is exempt too** — it grants nothing (approval needs a logged-in session) and is bounded by the 10 req/min/IP bucket + 5-min TTL. `CUSTOS_TURNSTILE_SECRET` and `CUSTOS_TURNSTILE_SITEKEY` are **both-or-neither** (startup validation); `CUSTOS_TURNSTILE_HOSTNAMES` **required when Turnstile is enabled** — comma-separated allowlist matched against the Siteverify payload `hostname` — **set it to the public browser origin(s) of the console, not the bind host** (mismatch → reject; **missing `hostname` in the Siteverify payload → reject**; independent of `CUSTOS_ALLOWED_ORIGINS`, which governs WebAuthn origins). Verdict failure or Siteverify error → **422 `turnstile_failed`**, audited `auth.failure` (audit only, no `auth_events` row), counts toward the per-IP request limiter but never credential lockout. **Siteverify contract: POST with `secret`, `response`, and `remoteip` = the §5-resolved client IP; fixed 5 s timeout; `success: false`, any error-codes (including token already-spent), timeout, or transport error → reject** — fail closed (outage blocks login; escape = unset both envs in a maintenance window). `GET /api/auth/status` is **unauthenticated and public** (`turnstile_sitekey` is a public widget key by design) and returns `{setup_required, totp_required, turnstile_sitekey|null, passkey_available}` (+ `csrf_token` with a live session, §3).
- **CLI auth with Turnstile (device hand-off, normative):** `POST /api/auth/device` (unauthenticated, rate-limited; **≤5 live unconsumed rows per client IP — mint beyond that → 429 `rate_limited`**, so a same-IP flood cannot starve the operator's own hand-off) mints a **device code** (≥128-bit, TTL 5 min, `device_codes` row) and returns **`{device_code, expires_at}` only — the CLI builds the console URL itself** from its own `CUSTOS_URL`: `<CUSTOS_URL>/device#<code>` (route pinned in §8; the server never needs to know its public origin). The CLI opens it (**device code travels in the URL fragment** — out of logs/referrer/history; it travels in approve/exchange bodies, never logged (§3); **the device page strips the fragment via `history.replaceState` immediately after reading it**) and prompts the operator for the transfer code. The operator logs into the console normally (Turnstile there); the console's device page **fetches `POST /api/auth/device/lookup` (session + CSRF, body `{device_code}`) → `{client_ip, user_agent, expires_at}` or 404** and shows the minting client's IP and user agent for human confirmation — the page warns that approving an uninitiated request hands the requester a session. On confirmation it calls **`POST /api/auth/device/approve`** (session + CSRF; device code from the fragment) — **single approval per row: a guarded UPDATE (`approved_by_session IS NULL` → set) rejects re-approval of an already-approved row (409 `conflict`)** and **extends the row: `expires_at = max(expires_at, now() + 2 min)`** — so the transfer code always gets its full 2-minute window; exactly one transfer code ever exists per device row. Approval generates the **transfer code** (**≥128-bit, SHA-256 `transfer_hash`, constant-time compare, TTL 2 min after `approved_at`; **the 5th attempt is the last — consume requires post-increment `exchange_attempts` ≤ 5; a 6th try sees the row dead**; each try is a guarded increment; consume is the guarded UPDATE below**) bound to that row (`approved_by_session`) and displays it once **with the exchange deadline (2 min from approval); the CLI prompt shows the same deadline**. The CLI submits `{device_code, transfer_code}` to `POST /api/auth/device-exchange`; both must match the same live row — **the exchange window is `min(device expires_at, approved_at + 2 min)` — approval extends `expires_at` (above), so this is always the full 2 minutes** → **then a second guarded UPDATE consumes the row (transfer code already verified in application code via `compare_digest`, §4)** (`WHERE consumed_at IS NULL AND exchange_attempts <= 5 AND <within window>` — post-increment, so exactly five tries; concurrent correct exchanges: exactly one winner; **both UPDATEs are single guarded statements (atomic row-level compare-and-set), never read-increment-write in application code**; wrong codes burn attempts; **dead/expired/consumed rows all return the same 401**), a **`full` session** issued with **shortened TTLs: idle 1 h / absolute 12 h** (`idle_ttl_seconds` column, §4 schema; step-up does not extend them); response `{session cookie, csrf_token}`. Expired/consumed/mismatched → 401; an approving login never satisfies a different device row. **Lookup/approve on an already-consumed row → 404/409 respectively, audited `device.login` `ok: false` (benign audited miss); approval survives later session revocation (code already displayed; ≤2-min window bounds it).** Both unauthenticated endpoints: 10 req/min/IP bucket; all three audited `device.login`. Interactive CLI step-up then uses the password prompt over that session (step-up is Turnstile-exempt).
- **Sessions:** opaque cookie (`custos_session` = **32 random bytes base64url**, SHA-256 hash server-side) + CSRF header on cookie-authenticated mutations; **idle TTL 12 h** (`last_seen_at` refreshed on any authenticated request) / **absolute TTL 7 d**; logout and password change invalidate all sessions **and cascade-delete their unconsumed step-up tokens** — **including the performing `full` session** (the password-change response mints one fresh replacement session so the console stays logged in; the `recovery_reset` promotion below is the other exemption); **password change and both break-glass resets (`reset-password`, `reset-mfa`) also revoke all operator tokens and mark all unconsumed recovery codes consumed** (compromise recovery — a stolen password+code pair must not survive the rotation; the operator re-issues codes at next TOTP confirm/regen; **both break-glass resets also invalidate all sessions/step-up tokens** — §9); **agent keys are never revoked by operator credential resets** (rotation is per-key via revoke — mass revocation would break every working agent on an operator password change). The `recovery_reset` session performing the password change is exempt from **session invalidation** only — it is promoted (below).
- **TOTP:** `pyotp`, issuer `Custos`, ±1 step; **replay guard applies at every verification site with per-site counters (`login`, `stepup` = the step-up endpoint, `confirm` = TOTP confirm; all start at 0): reject any presented step ≤ the site's stored step; acceptance is a guarded `UPDATE … SET <counter> = :step WHERE <counter> < :step` committed in that request's transaction before the credential effect** (one winner per site; a code may be accepted once at each distinct site within the ±1 window — cross-site replay is the accepted residual, bounded by the window and the password requirement; **an older step within ±1 is rejected at a site that already accepted a newer one — the operator waits ≤30 s for the next code; that rejection is the ordinary 401 credential-failure shape, feeds lockout**); secret sealed per §4 operator domain; enable/confirm/disable require step-up; 10 recovery codes issued at enable. **Unreadable/missing-version TOTP blob:** login and step-up TOTP verification → **500 `key_unavailable`** (not the 401 shape; **no `auth_events` row** — nothing was verified; **this distinguishes broken-TOTP from wrong-credentials — accepted residual: availability debugging beats a marginal oracle**); **Escape paths that need no keyring: recovery-code login (password + code — still pepper-dependent) or break-glass `custos account reset-mfa` (direct DB, needs neither). When the TOTP blob is unreadable AND no unused codes remain, `reset-mfa` (host-shell access) is the only path back to a working step-up factor — a remote-only operator in that state must obtain shell access or restore from backup; stated here so the runbook order is unambiguous (§13).**
- **Recovery codes:** 10 codes, each **16 chars from the canonical Crockford alphabet `0123456789ABCDEFGHJKMNPQRSTVWXYZ` (exactly these 32 symbols — I/L/O/U never generated; 5 bits/char, 80-bit entropy)**; normalization = uppercase, strip dashes/spaces, map I/L→1, O→0 before HMAC (§4 contract) — **any other non-alphabet character (including U) → validation failure, same identical 401**; — **a bijection on stored codes** (canonical alphabet excludes the mapped letters), so no entropy loss or collision between issued codes; **verification loads all unconsumed rows and constant-time-compares each digest** (no searchable index on HMACs; ≤10 rows). Consume is a single guarded UPDATE (`consumed_at IS NULL` → set): concurrent use yields exactly one success. **Regeneration and `reset-mfa` mark prior unconsumed codes consumed** (soft, audited count — never delete rows). Recovery login (username + password + code, above) creates a **`recovery_reset` session** (`purpose`, **TTL 30 min**, no idle extension): it may call only password change, TOTP/passkey/recovery management, and step-up — **`purpose` is checked server-side after authentication on every route; anything else → 403 `purpose_denied`**. **Within it, step-up is waived for password change only — but that password change still requires re-entering and verifying the current password in the body** (a stolen recovery-reset cookie alone cannot promote); other credential management uses **password + an unused recovery code** (the normal password+TOTP path also works if TOTP is functional; a code is consumed on success — the 10-code budget bounds this path; password alone never suffices). After a successful password change the session is **promoted to `full`** (fresh TTLs, all other sessions invalidated) in the same transaction. **Promotion atomically disables TOTP and issues 10 fresh recovery codes** (returned once in the password-change response; recovery login proved code possession; never leave zero step-up factors; re-enable TOTP from Settings). Zero codes left + lost password = break-glass `custos account reset-password` (below). **A recovery login consumes the last code and still yields the `recovery_reset` session — promotion needs only the current password (waiver), so promotion is always reachable; the zero-factor state exists only after promotion, which itself issues fresh codes.**
- **Passkeys:** register/list/remove require step-up; **sign-count rule (WebAuthn-correct): reject only when both stored and asserted counters are non-zero and asserted ≤ stored** (counter-0 authenticators work); multiple credentials allowed. `CUSTOS_WEBAUTHN_RP_ID` + `CUSTOS_ALLOWED_ORIGINS` required for passkey endpoints — **unset = passkey endpoints return 404 and `auth/status.passkey_available: false` (not a startup failure; the product works password+TOTP-only); exactly one set → startup failure (both-or-neither).** **Dev exception (pinned): when `CUSTOS_INSECURE_DEV=1`, RP ID may be `localhost` and allowed origins may be `http://localhost[:port]` / `http://127.0.0.1[:port]` (loopback only, startup warning logged); no other insecure origin is ever accepted.**
- **Lockout (normative numbers):** sliding window **15 min**; per-IP: **10 failures → 15 min block** (`Retry-After`); per-account: **30 failures → 30 min block**, non-extending under continued attack (bounds the DoS; slower online attack during blocks accepted for a single-operator product). **Order on credential endpoints: lockout check → request limiter → Turnstile siteverify → credential checks** — 429 gates reject before any Siteverify call; lockout wins over bucket (`locked_out`). 429-rejected requests never verify credentials and write no `auth_events` row; only verified-and-failed credentials count.** **`setup` failures feed the per-IP credential block; escape = `custos account unlock`.** Counted kinds: `login_password`, `login_totp`, `login_passkey`, `login_recovery`, `step_up`, `setup`. Escape: `custos account unlock` (below) — inserts a `lockout_suppressions` marker so lockout queries ignore ledger rows at or before the marker ts (rows never deleted). Client IP: `CUSTOS_TRUSTED_PROXIES` (CIDR list; **startup validation rejects malformed CIDRs and any `/0`; host bits are normalized (`strict=False` — `127.0.0.1/32` and bare `127.0.0.1` both valid)**; **required non-empty when `CUSTOS_PUBLIC_BIND=1`**; startup failure). **Same-host reverse-proxy topology (loopback bind, proxied traffic): the operator must also set `CUSTOS_TRUSTED_PROXIES=127.0.0.1/32` (or `::1/128`) — documented in §13 and the compose snippet (operator contract — undetectable server-side)**) — **unset = ignore forwarded headers**; when set, **forwarded headers are honored only if the direct remote address is inside `CUSTOS_TRUSTED_PROXIES`** (any other peer's `X-Forwarded-For` is ignored — no spoofing from untrusted containers/clients); then walk `X-Forwarded-For` right-to-left skipping trusted hops, first untrusted address wins; **all-trusted chain → fall back to the direct remote address**. **The trusted-hop test uses the numeric peer address of the connection (never names); in container topologies set the proxy's actual network CIDR, not loopback. Every `auth_events` row records both the direct peer and the resolved client IP — a mis-set allowlist is diagnosable from the ledger.**
- **Step-up:** `POST /api/auth/step-up` with **`{password, totp?}` — password plus TOTP when enabled (same factor set as login; neither-factor → 401 `step_up` failure; password alone cannot disable TOTP or reveal secrets) — or `{password, recovery_code}` as the emergency alternative (the code replaces the TOTP factor, never the password — same rule as login)** (constant-time verify first; **consumed atomically only on success** — failed step-ups never burn codes; a spent code forces the password+TOTP path or break-glass) → single-use token (`x-step-up-token` header), **TTL 5 min**, bound to the requesting session **or operator token** (`step_up_tokens` FK, exactly one). Consumption requires **the presenting principal to equal the bound principal** and re-validates it is still live — a stolen token is useless from another session. **Accepted residual: while TOTP is disabled (fresh setup, post-promotion, post-`reset-mfa`), step-up is password-only — single-factor reveal is possible in that window; §13's break-glass ordering minimizes it.** Required for: key mint/revoke, operator-token mint/revoke, purge, force-drop, rekey (first batch, §4), retention, secret/history reveal, **admin env export**, **secret→plain downgrade**, password change, TOTP/passkey/recovery management — **except password change within a `recovery_reset` session** (waiver above). Failures feed lockout.

### Operator tokens (CLI)

`co-<key_id>.<secret>`, same entropy/HMAC mechanics, **separate table**. Admin plane access; **`expires_at` mandatory for every operator token (max lifetime 90 days; mint rejects absent expiry)**. Step-up-gated actions require `allow_sensitive: true`, which substitutes for the step-up header **only on: reveal, history reveal, admin env, rekey (all batches), rekey verify, restore, secret→plain downgrade**. **`purge`, `force-drop`, and `retention` are session + step-up only — no token path**. **`allow_sensitive` tokens are additionally capped at 30 days**. **Accepted residual: a stolen plain admin token can overwrite/soft-delete items and roll the history window within its bounded lifetime, and read all names/notes/plain values/audit (metadata is cleartext by design); it cannot hard-delete, mint credentials, or prune the ledger.** Mitigations: expiry, revocation, audit. Token item-scopes: v2 candidate (§12). **Account-management (password/TOTP/passkey/recovery) and any mint/revoke of keys or tokens are session-only** — no token, however flagged, can register a passkey or mint credentials (no takeover / self-escalation path). **Server-enforced: any bearer-token request to a session-only route (including purge/force-drop/retention) → 403 `session_required` before any state check, audited `auth.failure`** — the CLI's interactive-login fallback is convenience, not the control. Minting operator tokens requires an interactive session. `allow_sensitive` use is marked in audit (`detail.allow_sensitive`). Revocation immediate; **expiry mandatory (above) — mint rejects absent or over-cap expiry**. **Invalidation is `revoked_at`, never row deletion; step-up/run-token invalidation is an explicit `DELETE FROM step_up_tokens WHERE <bound principal> AND consumed_at IS NULL` executed in the same transaction as the revocation/password change** (a revoked session never leaves a live multi-use run token; in-flight cursors are inert without a live token). Default CLI tokens manage items and read audit; sensitive ops prompt for interactive login. **Residual: a stolen `allow_sensitive` token reads cleartext within its bounded lifetime; it cannot destroy data or erase the record.**

### Rate limits (normative)

- Agent plane: 120 req/min/key, 8 concurrent (in-process; single-worker contract §3). MCP tool calls count against the same bucket.
- Unauthenticated endpoints (login, setup, passkey assertion, **device, device-exchange**): **10 req/min/IP** (setup: 3/min/IP) + lockout above (step-up is authenticated; its failures feed lockout); failed agent auth: **30 failures/min/IP → 429**; **global failed-auth ledger budget: 600 `auth_events`+`audit` failure rows/min process-wide — beyond it, failures still 401/429 but are not ledgered; lockout then evaluates against an in-process sliding failure counter (same 10/15, 30/30 numbers) so blocks still trip under a flood; budget exhaustion logged once/min without values**. **Global Argon2 semaphore: at most 2 concurrent password/recovery-hash verifications process-wide** (queue wait cap 10 s → 429 `rate_limited`).
- Admin plane: 300 req/min/session-or-token.
- Exceeding → 429 `rate_limited` with `Retry-After`.

### Write body (canonical, normative)

Item writes (POST/PUT) carry `{name?, notes, fields: [{name, secret, value}]}` — an **array**, not a map (duplicate names → 422). **POST requires `name`; PUT/PATCH must omit `name` or match the path exactly, else 422 `invalid`; scope is always evaluated against the path name (POST: body name); rename does not exist in v1.** **`notes` on PUT is required** (string; `""` clears — absent → 422 `invalid`, so a masked round-trip cannot silently drop notes; the masked admin get returns full notes for exactly this). PATCH carries `{notes?, fields?: [{name, secret?, value}]}` where `value: null` removes the field; **`fields` optional/`[]` = no field changes; a notes-only PATCH is legal, bumps `revision`, audited `patch`**; **absent `notes` = keep, `notes: null` = clear, string = replace**. **PATCH `secret` omission on an existing field = keep the current flag** (never defaults to plain). **Entry semantics, single precedence rule (existing field): `value` absent + `secret` absent → keep both (no-op); `value` absent + `secret` present equal to the current flag → keep value (masked round-trip); `value` absent + `secret` present differing from current flag, or `value` absent on a `plain` field → 422 `invalid`; `value: null` → remove; `value` present → set (flag change only via the sanctioned pair).** On a new field both `secret` and non-null `value` are required → else 422. **PATCH duplicate names are allowed only as the sanctioned remove-then-add pair** (`value: null` entry followed by one add entry for the same name; any other duplicate → 422). **Ops apply in array order against the intermediate state; the add entry after a remove must carry explicit `secret` and non-null `value` (keep/omission semantics never apply to it — the row it would keep is already gone) → else 422.** **A single entry changing an existing field's `secret` flag without the pair → 422 `invalid`** (in-place flag change does not exist). **Retype:** `plain→secret` is allowed for agents via that pair (executed as one delete+insert transaction, history kept). **`secret→plain` is refused on the agent plane (403 `secret_downgrade_denied`) for PUT and PATCH alike — a request containing any downgrading op fails atomically, nothing partially applies. **Downgrade detection is a per-name pre/post classification table: for every name appearing in the request, compare its `secret` flag at request start (absent = not secret) with its flag after all ops apply (absent = removed, not a downgrade). Secret→plain in that table = downgrade, regardless of how the ops got there — the sanctioned remove+re-add pair with `secret: false` is exactly the representable downgrade case and is refused (agent 403) / gated (admin step-up).** On the admin plane the same pre-request rule requires step-up/`allow_sensitive` **in that request** (401 `step_up_required`, atomic). Cross-request boundary (explicit, agent plane only):** the refusal detects downgrades of *currently existing* secret fields within one request; remove in one request, re-add as plain in a later request is **not detectable as a downgrade** — it is indistinguishable from legitimate reuse of a freed name, and the classification boundary above already grants read-write keys that power. The old secret value remains in history either way. **The admin gate is request-shaped:** detection uses the same pre-request-state rule (a remove+re-add pair within one request cannot bypass it); a plain re-add in a *later* request after an earlier explicit remove is an ordinary create — **accepted residual, symmetric with the agent-plane cross-request boundary: a principal that can remove a secret field can already destroy it; the gate prevents accidental single-request downgrades, not a determined two-request rewrite by an authorized writer.** On PUT, a `secret` flag change on an existing field is treated as remove+add: **`plain→secret` allowed (same as PATCH retype); `secret→plain` follows the pre-request rule (agent: 403; admin: step-up)**. **Value omission on PUT/PATCH entries:** governed by the single precedence rule above — `{name, secret: true}` with no `value` keeps the existing sealed value only for an existing secret field with no flag change; POST always requires explicit values. `value: null` = remove. PUT wholesale-replace keeps omitted-value secret fields, drops fields absent from the array (history kept). **Classification boundary (explicit):** `secret` is an operator policy label, **not a confidentiality control against read-write keys** — such a key can read a value and write it anywhere in scope; the downgrade refusal prevents *accidental* cleartext persistence, not exfiltration. The §4 item cap is measured on the resulting item's canonical JSON.

## 9. CLI

`custos` (Rust binary, `cli/` crate; crates: `clap`, `reqwest`/rustls, `serde`, `tokio`, plus `tokio-postgres` + `argon2` for break-glass only). Auth: **`custos login` uses the direct username/password/TOTP prompt flow when Turnstile is unset; when `/api/auth/status` reports a sitekey it automatically uses the device hand-off (§5)** — direct login against a Turnstile-gated server is not attempted. `CUSTOS_OPERATOR_TOKEN` env is the non-interactive path (**client-side credential; the server never reads this env**). **Credential precedence when both a token and a session file exist: the env token is used for token-permitted routes; session-only routes (mint/revoke, purge, force-drop, retention, account management) use the session file, prompting interactive login if absent/expired — the two are never sent on one request** (server rejects that combination, §3). **An expired/revoked env token fails its request with the normal 401 surfaced verbatim — no silent fallback to the session file** (the operator fixes the env or unsets it). Session storage: `$XDG_CONFIG_HOME/custos/session.json` (default `~/.config/custos/`), file mode **0600**, dir 0700; OS keychain when available, file fallback.

- `custos item list|get|set|rm|restore|purge|force-drop|history` — **`set` reads fields from stdin JSON or a 0600 file (`--fields-file`); secret values are never accepted as argv flags** (shell-history/`ps` discipline; plain fields may use flags); `get` masks secrets unless `--reveal` (step-up); `force-drop` deletes unreadable rows (§4 degraded mode).
- `custos key mint --label X --mode read|read-write --scope 'a' --scope 'b-*' [--expires …]`, `custos key ls|revoke` — interactive step-up (password+TOTP, or password+recovery code).
- `custos token mint|ls|revoke` — interactive login only (§5 no-token-minting rule).
- `custos env <item>` — prints `export KEY='value'` lines. **Field-name grammar `^[A-Z][A-Z0-9_]{0,63}$` (schema-enforced); value escaping: wrap in single quotes, replace every `'` with `'\''` (close-quote, escaped-quote, reopen-quote — the standard POSIX idiom; a value like `'; cmd; echo '` stays fully inside the quoted string)**; values containing NUL are rejected at write time. Safe for `eval` against adversarial values (unit + E2E tested). **Name hazard (explicit boundary):** `export PATH=…`, `LD_PRELOAD=…`, `IFS=…` etc. can subvert the evaluating shell regardless of value escaping — the grammar cannot exclude them without breaking legitimate credential names; the fixed hazard rule is **a deny-set plus deny-patterns, maintained in code**: exact names `PATH`, `IFS`, `BASH_ENV`, `ENV`, `PROMPT_COMMAND`, `CDPATH`, `SHELL`, `PS1`, `GLOBIGNORE`, `NODE_OPTIONS`, `PYTHONPATH`, `PYTHONSTARTUP`, `PERL5OPT`, `RUBYOPT` **plus patterns `LD_*`, `DYLD_*`, `*_OPT`, `*_OPTIONS`, `PYTHON*`** (best-effort; coverage claim = value escaping, §6). `custos env` **warns on stderr when the server refused any hazardous line** and maps `--allow-hazardous-names` to the query flag **on the admin endpoint (`custos env` is operator-plane, §6 — the flag needs an `allow_sensitive` token or interactive step-up, same as `--reveal`)** — **the refusal itself is server-side (§6 env endpoints): on the agent plane hazardous names are always emitted commented-out (no override); the admin-plane endpoint honors `allow_hazardous=1` under step-up/`allow_sensitive`** (unit-tested); the eval-safety claim covers **value escaping only** — a read-write agent that can plant a hazardous *name* is inside the same trust boundary as one that plants a hostile value the operator then uses. Claim: *no secret in the command line or shell history*; exported vars are visible to child processes — that is injection's point.
- `custos audit [--actor …] [--item …]`, `custos rekey` (loops batches until `remaining: 0`), `custos retention`.
- `custos account unlock|reset-password|reset-mfa|retention` — **local-process break-glass, not an API call** (`retention` here runs the same prune SQL directly — the emergency path when no session can be obtained; audit `retention`, actor `local_process`): connects directly to PostgreSQL (**`tokio-postgres`; accepts a standard `postgresql://…` DSN** — the CLI strips the `+asyncpg` driver marker from `CUSTOS_DATABASE_URL` if present) with a DSN from `CUSTOS_DATABASE_URL` in the operator's shell **or `--database-url-file` (0600 file) — no `--database-url` argv flag (the DSN carries a password)** (host shell access is the authorization). Sanctioned raw-write exception to the ORM rule: **Argon2id PHC output must be byte-compatible with the server verifier — pinned: argon2id v0x13, m=65536 KiB, t=3, p=4, salt 16 random bytes, hash 32 bytes, standard base64 PHC encoding; unit test: CLI-written hash authenticates through the server's `argon2-cffi` verify**. `unlock` inserts `lockout_suppressions` markers for **the account scope and `ip:*` (wildcard — no enumeration of blocked IPs needed; rotating-source attacks covered)** (or `--ip <addr>` for one IP instead of the wildcard) so no derived window survives (audit `account.unlock`); `reset-password` **prompts for the new password on a hidden TTY prompt or reads it from stdin — never an argv flag** (shell-history discipline); it sets a new Argon2id hash, invalidates all sessions/step-up tokens, **revokes all operator tokens, and marks all unconsumed recovery codes consumed** (audit `operator.password_change`, detail `break_glass`, `codes_consumed: n`); **`reset-mfa` disables TOTP, removes passkeys, marks all recovery codes consumed (consume-not-delete — forensic rows stay), revokes all operator tokens, and invalidates all sessions/step-up tokens** (attacker-minted sessions die with the attacker-added factors; the operator re-logs in with password alone — TOTP is now off; **reset-mfa writes exactly three audit rows — `operator.totp_change`, `operator.passkey_change`, `operator.recovery_regen` (the latter carries `codes_consumed: n`)** — all detail `break_glass`). Agent keys are kept in both (same rationale as password change, §5). Actor: `local_process` / `"local"` (§4).
- Sensitive ops: `allow_sensitive` tokens cover **only the enumerated ops (§5: reveal, history reveal, admin env, rekey, downgrade)**; **purge/force-drop/retention and key/token mint/revoke always fall back to interactive login + step-up** regardless of token flags.

## 13. Operations

- **Backup:** nightly `pg_dump` **plus** off-box copies of keyring and pepper — **produced by host cron / external tooling, outside the service** (§2's no-workers rule applies to the app, not the host); cadence and storage are the operator's, the design only pins the unit and the sensitivity. **The dump is sensitive** (cleartext metadata/plain values/audit/hash) — encrypt off-box, restrict like the keyring. **Keep all old keyring versions in the backup copy** (append-only keyring history): a dump taken mid-rekey then stays readable even if the live env has already dropped an old version. Restore = load dump, restore pepper + a keyring containing every version the dump references, start (startup validation §4 catches gaps), verify by reading one known item.
- **Keyring rotation:** add `k<n+1>`, restart, `custos rekey` until `remaining: 0` **and `skipped: 0` on the final batches** (`skipped > 0` means undecryptable rows — restore the missing key version or `force-drop` the affected items (drops unreadable history too; **`pg_dump` first — force-drop is irreversible**), then rerun; a final full pass with `skipped: 0` proves none remain), verify `custos rekey --audit` shows no rows under old versions **(claim scoped to version migration; corruption under the newest version is proven only by `custos rekey --verify`)**, then remove old versions. Removing a still-referenced version is caught at next startup (refusal, §4) — never silent. **Restore-from-older-dump runbook: load the dump, restore the backup keyring (it contains every version the dump references — including versions newer than the current live keyring), start; if a version is genuinely lost, start with `CUSTOS_ALLOW_MISSING_KEY_VERSION=1`, run `custos rekey --audit` to list affected versions/items, `force-drop` or accept degraded reads, then rerun rekey.**
- **Pepper rotation (manual, v1):** maintenance window; rotate pepper; all agent keys, operator tokens, and recovery codes invalid — re-mint keys/tokens and **re-issue recovery codes**. **No credential-path re-issue exists while old codes are dead (regen needs a step-up the dead codes cannot satisfy): the maintenance window ends with break-glass `reset-mfa` + `reset-password`, or a TOTP-functional operator regenerates from Settings.** **Threat note: stolen pepper + dump enables offline brute-force of password and recovery codes — protect the pepper like the keyring.** **Pepper rotation is not a credential reset: it invalidates every HMAC digest at once; stored digests are never re-hashed in place (the old secrets are not recoverable from them) — every key/token/code is re-minted fresh. No dual-pepper window in v1; the uniform 401 for stale digests is intended.** The TOTP secret is keyring-sealed and **unaffected** (do not disable/re-enable TOTP); operator password (Argon2) and sessions (cookie SHA-256) are pepper-independent and survive.
- **Post-restore credential reset (mandatory):** an older dump resurrects revoked keys/tokens, consumed recovery codes, and old sessions/password state. After any restore: revoke all agent keys and operator tokens minted after the dump (or rotate the pepper to invalidate everything), invalidate all sessions, re-issue recovery codes, and audit the reset (`local_process`). Verify by reading one known item.
- **Break-glass ordering:** locked out → `custos account unlock`; lost password → `reset-password` (then re-login, re-issue codes); lost/attacker-controlled MFA → `reset-mfa` — **which leaves password-only login: immediately follow with `custos account reset-password` (fresh password) and re-enable TOTP + fresh codes from the console**; the account is in a weakened state until then.
- **Retention cadence:** `custos retention` **run interactively by the operator (suggested monthly)** — it is session + step-up only (§5), so no unattended cron path exists by design; nothing prunes automatically (§2 no workers). `CUSTOS_RETENTION_DAYS` has no effect until the command runs.
- **Reverse proxy on the same host:** set `CUSTOS_TRUSTED_PROXIES=127.0.0.1/32` (or `::1/128`) even with a loopback bind — otherwise all clients share the proxy IP and lockout becomes a global self-DoS (§5).
- **Turnstile outage:** login fails closed; escape = unset `CUSTOS_TURNSTILE_SECRET`, `_SITEKEY`, **and `_HOSTNAMES` together** in a maintenance window (both-or-neither validation, §5; documented, audited via deploy change).
